# Module A, Milestone 1 — Payments Data Model & KPI Layer

## 0. Scope boundary

This milestone builds a **payments funnel data model and SQL-first analytics
layer** (KPIs, funnel, retry/recovery, segmentation, rule-based fraud
guardrails) on top of the same IEEE-CIS Fraud Detection dataset used by
Module B. It does **not** train any machine-learning model — "guardrails"
below are fixed, documented business rules (thresholds on raw/derived
fields), not a fitted classifier. It does not touch Module B's split,
features, or models; it is a new, independent module that happens to read
the same raw CSVs.

## 1. Why a synthetic layer is needed at all

IEEE-CIS's `train_transaction`/`train_identity` tables contain **one row
per realized, recorded transaction** — there is no concept in the public
dataset of a checkout session, a declined authorization attempt, a retry,
or an abandoned cart. A payments funnel (initiated → attempted → declined
→ retried → authorized/abandoned) genuinely does not exist in this data.

To demonstrate payments/product-analytics reasoning (funnels, retry
economics, segmentation, guardrails) at all, this milestone adds a
**synthetic session/attempt layer** on top of the real transaction rows.
This is stated explicitly and repeatedly in this document and in the code
itself (module docstrings, column-level labels) so nothing synthetic is
ever mistaken for an empirical finding about real payment behavior. Every
synthetic generation choice (probabilities, time windows, decline-reason
vocabulary) is a value chosen by the author for illustration, recorded in
`configs/payments_synthetic_assumptions.json`, and is explicitly **not**
fit to, or sourced from, any real payments company's data.

This mirrors the same honesty standard Module B applies to masked
IEEE-CIS columns (`docs/data_dictionary.md`): real data is labeled real,
invented data is labeled invented, and the two are never blended without
a visible seam.

## 2. Real vs. synthetic field inventory

### 2a. Real fields (from IEEE-CIS, unmodified values)

| Field | Source | Status per `docs/data_dictionary.md` |
|---|---|---|
| `TransactionID` | `train_transaction` | Real identifier |
| `TransactionDT` | `train_transaction` | Real, documented as timedelta-from-undisclosed-reference (not wall-clock) |
| `TransactionAmt` | `train_transaction` | Real, documented (USD) |
| `ProductCD` | `train_transaction` | Real, documented category, per-code meaning undisclosed |
| `card4`, `card6` | `train_transaction` | Real, documented category ("card-related"), exact per-column meaning undisclosed — used here only as opaque categorical segmentation keys, never interpreted as "network" or "credit/debit" per Module B's existing rule |
| `P_emaildomain`, `R_emaildomain` | `train_transaction` | Real, documented; combined into `email_domain_match` (reused unmodified from `src.features.categorical_features.add_email_domain_match`, the same Module B function, applied here with no new logic) |
| `DeviceType` | `train_identity` | Real, documented category; `None`/missing when no identity record |
| `isFraud` | `train_transaction` | Real label. Same provenance caveat as Module B: its determination process is taken as given, not re-derived. **Only available for real-linked sessions** (see §3) — a session with no real transaction has no fraud determination, by construction, not by omission. |

No masked (`C*`/`D*`/`M*`/`V*`/`id_*`) column is used anywhere in Module A,
for the same reason Module B defers them: undocumented per-column meaning,
unresolved point-in-time-safety status for some of them. Module A does not
need them for a funnel/KPI/segmentation layer.

### 2b. Synthetic fields (generated by `src/payments/generate_sessions.py`)

| Field | Entity | What it represents | Labeled synthetic because |
|---|---|---|---|
| `session_id` | session | Synthetic surrogate key | Invented grain; no such entity in IEEE-CIS |
| `transaction_id` | session | FK to real `TransactionID`, nullable | Null for the ~`abandonment_rate` fraction of sessions that are entirely synthetic (see §3) |
| `is_synthetic_abandonment` | session | Whether this session has zero real-transaction linkage | Explicit flag so no downstream query can silently treat an invented session as real |
| `final_outcome` | session | `authorized` or `abandoned` | Invented funnel-terminal-state concept |
| `attempt_count` | session | Number of authorization attempts in the session | Sampled from `decline_before_success_probs` / `abandonment_attempt_count_probs` in the config — illustrative, not measured |
| `session_start_offset_seconds` | session | Synthetic time the session began (before its first attempt) | Derived by subtracting a sampled "form-fill" lead time from the first attempt's offset |
| `attempt_number` | attempt | 1-indexed position within the session | Invented grain |
| `attempt_offset_seconds` | attempt | Synthetic time of this attempt | For real-linked sessions, the **final** attempt's offset is pinned exactly to the real `TransactionDT` (the one fact IEEE-CIS gives us); every earlier attempt's offset is backed out via sampled retry gaps. For abandonment-only sessions, the final (give-up) attempt's offset is pinned to a bootstrap-sampled real `TransactionDT` value (see §3) so synthetic session timing still lives inside the real observed time window, rather than an arbitrarily invented clock. |
| `outcome` | attempt | `declined` or `authorized` | Invented; by construction, exactly the last attempt of a session with `final_outcome == 'authorized'` is `authorized`, every other attempt in every session is `declined` |
| `decline_reason_code` | attempt | One of a small illustrative vocabulary (`insufficient_funds`, `risk_block`, `issuer_timeout`, `invalid_card_details`, `other`) | **Not** real issuer/network decline codes — IEEE-CIS records no decline reasons at all. Sampled from fixed weights in the config, purely for funnel/retry narrative texture. Null exactly when `outcome == 'authorized'`. |
| `ProductCD`, `card4`, `card6`, `DeviceType`, `TransactionAmt`, `email_domain_match` (abandonment sessions only) | session | Copied from one randomly drawn real transaction ("donor row") | A synthetic session has no real transaction to source these from. Rather than inventing a new distribution for these fields, the generator clones an existing real row's categorical/amount profile wholesale, so synthetic sessions' segment mix resembles the real data's own — see §3 for why this is a donor *template*, not an additional real transaction (the donor's own real session is unaffected and still exists separately). |

## 3. Entity-relationship model

```
transactions (real, IEEE-CIS; grain: one row per TransactionID)
        │ 0 or 1
        │
        ▼ 1
payment_sessions (synthetic; grain: one row per session_id)
   - transaction_id is NULL for synthetic-abandonment sessions
   - exactly one session per real TransactionID (every real transaction
     IS the authorized outcome of exactly one session)
        │ 1
        │
        ▼ many (>= 1)
payment_attempts (synthetic; grain: one row per (session_id, attempt_number))
```

- **Grain of `transactions`**: one row per `TransactionID`, unmodified
  from IEEE-CIS. Read directly from `data/raw/train_transaction.csv` /
  `data/raw/train_identity.csv` via `src.data.loaders` (same DuckDB
  mechanism Module B's Milestone 1 uses) — Module A does **not** depend
  on Module B's processed `baseline_features_v1.parquet` or any
  Module-B-engineered feature, to keep the two modules independent.
- **Cardinality `transactions` → `payment_sessions`**: exactly 1:1 for
  real-linked sessions (every real transaction is modeled as the
  successful terminal attempt of exactly one session — IEEE-CIS gives us
  no information suggesting any real transaction is itself a retry of
  another real transaction, so this is the simplest defensible mapping).
  Additionally, `round(abandonment_rate * n_real_transactions)` extra
  sessions exist with `transaction_id = NULL` — entirely synthetic,
  representing checkout attempts that never converted. `abandonment_rate`
  is a single illustrative config constant (default 0.15), **not** an
  empirical cart-abandonment rate for any real business.
- **Cardinality `payment_sessions` → `payment_attempts`**: 1:many,
  `attempt_count >= 1` always. `attempt_count` is itself synthetic (§2b).
- **Determinism**: the whole generator is a pure function of
  (sorted real transaction rows, `configs/payments_synthetic_assumptions.json`,
  a single integer seed). Same inputs → byte-identical output, verified
  by `tests/payments/test_generate_sessions.py`. Input row order does not
  affect output (the generator sorts by `(TransactionDT, TransactionID)`
  internally first), also verified by an order-invariance test, mirroring
  the adversarial-leakage-test discipline Module B applies to its
  expanding-window features.

## 4. Why a donor-row approach for abandonment sessions (not a new distribution)

An entirely synthetic session (no real `TransactionID`) still needs a
`ProductCD`/`card4`/`card6`/`TransactionAmt`/email-match profile for
segmentation and guardrails to mean anything. Two options were considered:

1. **Invent a new distribution** for each of these fields (e.g. "25% `W`,
   20% `C`, ..."). Rejected: those percentages would have to come from
   somewhere, and inventing them would be exactly the kind of fabricated
   business assumption this project's working style forbids.
2. **Clone one randomly drawn real transaction's field values wholesale**
   (the approach taken). The donor row is drawn uniformly at random (with
   replacement) from the same real `transactions` table, using the
   generator's own seeded RNG. This guarantees the synthetic sessions'
   category/amount mix is drawn from an actually-observed joint
   distribution rather than an invented one, at the cost of not being a
   fully independent draw (donor rows can repeat across synthetic
   sessions). The donor's `TransactionID`, `isFraud`, and its own session
   are completely unaffected — cloning its field values does not consume
   or alter the donor's real session in any way.

This is recorded as a limitation in §9, not hidden: synthetic sessions'
segment mix is a resampling of the real mix, not an independently
reasoned product/channel assumption.

## 5. KPI dictionary

All KPIs are computed in `src/payments/kpi.py` via DuckDB SQL over the
`payment_sessions`/`payment_attempts` tables (SQL-first, per the project's
minimal-dependency preference for DuckDB's native SQL engine over
hand-rolled pandas aggregation).

| KPI | Definition | Denominator |
|---|---|---|
| `authorization_rate` | fraction of sessions with `final_outcome = 'authorized'` | all sessions |
| `session_failure_rate` | `1 - authorization_rate` | all sessions |
| `gross_attempt_decline_rate` | fraction of **attempts** (not sessions) with `outcome = 'declined'` | all attempts |
| `retry_rate` | fraction of sessions with `attempt_count > 1` | all sessions |
| `avg_attempts_per_session` | mean `attempt_count` | all sessions |
| `recovery_rate` | of sessions that saw at least one decline (`attempt_count > 1`), the fraction that still end `authorized` | sessions with `attempt_count > 1` |

`gross_attempt_decline_rate` and `authorization_rate`/`session_failure_rate`
are deliberately reported separately: they answer different questions
("how often does any given attempt fail?" vs. "how often does the whole
session ultimately fail?") and conflating them would hide the fact that
retries recover some initially-declined sessions.

## 6. Funnel definition

Stage `n` ("attempt `n` reached") = sessions with `attempt_count >= n`.
For each stage, `src/payments/funnel.py` reports:
- `sessions_reaching_stage` and `conversion_from_initiated` (stage count /
  total sessions) — monotonically non-increasing by construction (a
  session can't reach attempt 3 without reaching attempt 2).
- `declined_at_stage` / `authorized_at_stage` — how the attempts made at
  exactly this stage resolved.

This directly exposes drop-off: most of the funnel's "loss" is retry
exhaustion (abandonment-only sessions stopping after their sampled
`attempt_count`) plus the real sessions that happen to have
`decline_before_success` sampled high, both synthetic by construction —
**this funnel's specific drop-off shape is an artifact of the config's
sampled distributions, not an empirical finding about real checkout
abandonment.** This caveat is repeated in the milestone report.

## 7. Retry/recovery analysis

`src/payments/retry_recovery.py` reports, by number of prior declines
before resolution (0, 1, 2, 3, 4+): session count, recovery rate
(fraction reaching `authorized` — by construction 100% for real-linked
sessions since every real-linked session's last attempt is `authorized`,
and 0% for abandonment sessions since they never reach `authorized`), and
mean/median time-to-resolution (`last_attempt_offset - session_start_offset_seconds`).
Because recovery is deterministic given `is_synthetic_abandonment` in this
generator (a real-linked session *always* eventually authorizes, an
abandonment session *never* does), the "recovery rate by retry depth"
table's real content is the **mix** of real vs. abandonment sessions at
each retry depth, not an independent recovery probability model — stated
explicitly, not left implicit.

## 8. Segmentation

`src/payments/segmentation.py` slices the §5 KPIs by `ProductCD`,
`card6`, `DeviceType`, and `TransactionAmt` quartile bucket — the same
real, documented-category fields used in the real vs. synthetic inventory
above (§2a), so segmentation is always defined on real fields even when
applied to a mix of real and synthetic (donor-cloned) rows.

## 9. Fraud guardrails (rule-based, not a model)

`src/payments/guardrails.py` defines a small number of fixed threshold
rules over real + already-defined synthetic fields (thresholds in
`configs/payments_guardrail_rules.json`, not hardcoded):

- `velocity_flag`: `attempt_count >= velocity_attempt_threshold` (default
  3) — many authorization attempts in one session.
- `high_amount_flag`: `TransactionAmt` at or above the
  `high_amount_percentile` (default 0.95) of the **real** transaction
  amount distribution.
- `mismatched_email_flag`: `email_domain_match == 'MISMATCH'`.
- `combined_flag`: `velocity_flag OR (high_amount_flag AND mismatched_email_flag)`.

These are deliberately simple, auditable, hand-specified rules — not a
fitted classifier (no `.fit()` call anywhere in this module) — per the
explicit instruction not to train any new ML model in this milestone.

**Backtest scope limitation, stated explicitly**: only real-linked
sessions carry a real `isFraud` label (§2a). The guardrail
flag-rate/precision/recall backtest in `src/payments/guardrails.py`
therefore runs only on that subset. It is a **descriptive crosstab**
(how often does each rule fire among known-fraud vs. known-legitimate
real-linked sessions), not a predictive-performance claim, and is not
comparable to Module B's ROC-AUC/PR-AUC model evaluation — these rules
were never fit to any data, so there is no train/test leakage question,
but there is also no claim that they would generalize or that their
thresholds are optimal.

## 10. Limitations (full list)

- **The entire session/attempt/decline/retry layer is synthetic.** Only
  the fields in §2a are real. This cannot be a substitute for, or
  evidence about, any real payment processor's actual funnel.
- **Abandonment rate, retry-depth distribution, decline-reason vocabulary,
  and guardrail thresholds are all illustrative author choices**, recorded
  in config files specifically so they are visibly swappable, not measured
  from any real system.
- **Abandonment-session category/amount profiles are resampled real rows
  (§4), not an independently reasoned distribution** — their segment mix
  mechanically resembles the real data's mix by construction, which is a
  property of the generator, not a finding.
- **No fraud label exists for abandonment-only sessions** — the guardrail
  backtest (§9) and any fraud-rate-by-segment table that includes
  `isFraud` only ever covers the real-linked subset; this is called out
  wherever such a table appears.
- **`card4`/`card6` are treated strictly as opaque categorical keys**, per
  Module B's existing rule — this project does not claim they mean
  "network" or "credit/debit" anywhere, even though that mapping is
  commonly assumed in public Kaggle discussion of this dataset, because
  the competition's own documentation does not disclose it.
- **`TransactionDT`'s undisclosed reference point** means all synthetic
  attempt/session offsets inherit the same "relative, not wall-clock"
  caveat as Module B's time features.
- **No new ML model was trained or evaluated in this milestone** — the
  guardrails are fixed rules, not a classifier; this is a deliberate
  scope boundary set by the task, not a limitation of capability.
